# 中转服务 Linux x64 发布

发行物只支持 Linux x64（Intel/AMD，`linux/amd64`），镜像名 `ghcr.io/qmtdlt/easycopy-relay`。客户端使用独立的 `desktop-v*` 标签；服务端使用 `relay-v*`，不修改共享 Cargo 版本。发行版本和源码提交写入镜像 OCI labels。

## 文件与构建边界

- `.github/workflows/release-relay.yml`：手动验证及标签发布。
- `deploy/Dockerfile.release`：Rust **1.97.0** / Debian bookworm 构建，先执行 `cargo test --locked -p easycopy-protocol -p easycopy-relay`，再编译 release。运行镜像使用同系列 Debian，保留所需 glibc，不误把动态链接程序放进 scratch。
- `deploy/Dockerfile.release.dockerignore`：只允许 workspace 清单及 Rust 源码进入发布上下文，不复制本地数据、身份和构建缓存。
- `deploy/release/`：版本化 Compose 和独立部署说明的模板。
- `script/relay-package.py`：导出 `docker load` 可用镜像、渲染说明与 Compose、计算 SHA-256。
- `script/relay-smoke.py`：用随机命名的临时 Compose 项目执行容器验收，仅清理自己创建的容器和卷。

构建和测试在 GitHub `ubuntu-24.04` x64 runner 上完成；固定 Rust 版本并使用提交的 `Cargo.lock`。不要以本机 cargo 编译成功代替 Linux 镜像实测。基础镜像固定发行系列/工具链版本，但未固定 digest，因此不是逐字节可复现构建；附件哈希用于核对这一次发行物。

原有 `deploy/Dockerfile`、`Dockerfile.offline`、`compose.yaml`、`compose.snap.yaml` 和[Ubuntu 部署记录](Ubuntu部署记录.md)保持原用途。macOS 对已有服务器的构建仍按记录使用离线流程；本发行流水线不连接服务器。Windows 本机构建另见[Windows 构建与部署方案](Windows构建部署方案.md)。普通重启无需构建。

## 手动验证（不会发布）

代码提交并推送到 `main` 后运行：

```sh
gh workflow run release-relay.yml --ref main
gh run list --workflow release-relay.yml --limit 5
gh run watch <运行编号> --exit-status
gh run download <运行编号> --dir relay-artifacts
```

也可在 Actions 页面选择 **Release relay Linux x64 → Run workflow**。手动模式没有发布选项，版本为 `validation-提交短哈希-运行编号-重试编号`，只上传保留 14 天的 Actions artifact。即使手动选择一个标签作为 ref，也不会进入发布 job。

产物：

- `easycopy-relay-linux-amd64-版本.tar.gz`：可直接 `docker image load`。
- `compose.yaml`：固定版本 `image:`，没有 `build:`。
- `README.md`（中文内容）：首次启动、配对、离线加载、备份、升级、回退。附件使用英文文件名，避免 GitHub 自动改名后与校验清单不一致。
- `compose.snap.yaml`：仅供已确认受影响的 Snap Docker 使用。
- `SHA256SUMS`：校验其余全部附件。

手动产物**未上传 GHCR**，运行时先加载 tar.gz，再用 `docker compose up -d --no-build --pull never`。临时验收凭据只存在独立临时卷及脚本内存中，不写入 artifact、日志或仓库。

验收会先导出镜像、删除本地镜像标签、再加载导出的 tar.gz，然后直接使用发行 Compose 验证：

1. 镜像必须为 Linux amd64；容器以 `10001:10001` 运行、根文件系统只读，权限限制、自动重启与日志轮转配置生效。
2. 空卷首次启动成功，内置认证 HTTPS 健康检查通过；两个空卷生成不同服务器身份和密钥。
3. 使用配对 CA 校验 TLS 和逻辑主机名，正确认证返回 200，缺失/错误认证返回 401。
4. 登记内容、上传中文文本载荷、下载并比较内容与 SHA-256。
5. 强制替换容器后，原配对串、元数据和载荷保持有效。

Rust 测试还覆盖 WSS 事件、上传中断/重试、取消、历史保留与身份持久化。镜像冒烟测试本身不覆盖桌面 UI、长时间压力、跨版本数据库迁移、Snap 实机或全量备份恢复。

## 首次正式发布

只有正式发行获得授权后才执行以下步骤；手动验收无需创建标签。

1. 确认目标提交的手动验证通过，并检查仓库 Actions 有发布 package 与 Release 的权限。
2. 选择独立服务端版本，例如 `0.1.0`，创建并推送 `relay-v0.1.0` 标签：

   ```sh
   git tag -a relay-v0.1.0 <已验收提交> -m '发布中转服务首版'
   git push origin relay-v0.1.0
   ```

3. 标签流水线重新编译、测试及验收，随后推送 `ghcr.io/qmtdlt/easycopy-relay:0.1.0`。仅推版本标签，不推 `latest`。含连字符的版本会标记为 GitHub prerelease；服务端 Release 不抢占桌面 Latest。
4. **首次 GHCR 包可能默认为 private。** 如匿名访问步骤失败，在 GitHub 账户 Packages → `easycopy-relay` → Package settings 中将 Visibility 设置为 **Public**，确认关联 `qmtdlt/EasyCopy` 并允许该仓库 Actions 写入，然后重跑失败 job。流水线会用空 Docker 登录配置检查匿名访问，未通过前不创建 GitHub Release。
5. 匿名访问通过后创建 Release 并上传上述附件。确认 Release 附件可匿名下载，Compose 可在独立 x64 主机拉取并启动后，再安排实际服务器升级。

GitHub 的包可见性说明见[官方文档](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)。公开源码仓库不作为 GHCR 已公开的证据。工作流无需个人访问令牌；仅标签发布 job 使用 `GITHUB_TOKEN` 的 `contents: write` 与 `packages: write`。

若 Release 创建或附件上传中途失败，先检查是否已有同名 Release 及附件；工作流不覆盖已有发行物，不通过删除正式标签来重试。根据失败阶段补齐附件前须核对原构建的 SHA256SUMS。

附件先上传至草稿 Release，下载全部附件与原产物逐字节比较并校验 SHA-256，通过后才公开；中转服务始终不设为 Latest，官网的 Latest 下载入口留给桌面客户端。
