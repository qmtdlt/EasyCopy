## 验收中发现并修复的问题

### 2026-11-03 用户反馈：Mac 连接 Ubuntu 失败，Windows 可连接

- 现象：使用 `192.168.1.48:8443` 和正确配对串，Mac 应用测试连接失败；用户报告 Windows 可连接。补全错误链后显示 `No route to host (os error 65)`。Mac 终端运行相同 Rust Transport 的 HTTPS/WSS 检查通过，系统设置中 EasyCopy 本地网络权限也已开启。
- 证据：原调试应用只有链接器生成的临时签名，签名标识为 `EasyCopy-fe247fb52995c12d`，`Info.plist=not bound`、`Sealed Resources=none`；系统网络日志同时出现该临时标识与 `com.easycopy.desktop`。应用身份不一致是本次重点修复项。Apple 也建议使用 Apple 签发的签名身份，以便系统可靠跟踪局域网权限：[TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)。
- 修复：`script/build_and_run.sh` 在启动前为完整应用包签名并校验，优先选唯一的 Apple Development 证书，显式签名标识为 `com.easycopy.desktop`；新增 `Info.plist` 提供 `NSLocalNetworkUsageDescription`；连接测试/保存保留完整错误链。新增只读 `check_connection` 示例，从标准输入接收配对串，不读剪贴板、不上传内容。
- 验证：`bash -n`、`plutil -lint`、`cargo fmt --all -- --check`、`git diff --check` 通过；`./script/build_and_run.sh --verify` 构建启动通过。签名检查确认 Apple Development 证书、正确应用标识、绑定的 Info.plist 和完整资源封签；原生 UI 显示“已连接”“设置已保存”，用户随后确认“测试成功了”。未更改系统本地网络权限开关或绕过证书验证，未重跑全量测试。
- 当前 Mac 客户端已连接 Ubuntu `192.168.1.48:8443`，原 `127.0.0.1:58444` 属于早期隔离验收环境。Windows 连接成功仅记录为用户反馈，本次没有操作 Windows 或验证双向剪贴板传输。

### 2026-11-03 用户反馈：Finder 复制文件出现 `/.file/id=…` 错误

- 原因：Finder 的 `public.file-url` 可以是文件身份引用。原实现直接用通用 URL 解析器转路径，错误地把 `/.file/id=…` 交给文件系统。此前原生探针仅覆盖普通路径 URL，未覆盖这一格式。
- 修复：`crates/client-core/src/clipboard/macos.rs` 先用 Foundation `NSURL.filePathURL` 解析真实路径，再进入文件准备/归档；失效引用返回明确错误。未变更源文件、连接配置或已失败历史记录。系统 API 依据：[Apple filePathURL 文档](https://developer.apple.com/documentation/foundation/nsurl/filepathurl)。
- 回归：使用独立原生 pasteboard，不改用户系统剪贴板。新增 4 项测试覆盖文件和嵌套/空目录归档、改名后引用、中文及 URL 转义字符、已删除引用和非文件 URL。修复前 3 项失败，修复后客户端核心全部 16 项通过；测试进程仍有 `sandbox_extension_consume` 警告，未影响断言。见[修复前](verification/file-reference-before.txt)、[修复后](verification/file-reference-tests.txt)。
- 实际验证：重新构建并启动 Mac 应用，在 Finder 选中合成测试文件和目录后按 Cmd+C；历史显示真实名称，上传状态为 `complete`，无错误，缓存内容与源文件 SHA-256 一致且空目录保留。见[应用截图](verification/file-reference-fixed.png)、[状态与哈希](verification/file-reference-live.json)、[构建日志](verification/file-reference-build.txt)。本次未测试微信；原失败记录需从 Finder 重新复制原文件创建新任务。

### 首轮验收

- Windows OpenClipboard(NULL) 缺少有效 owner：改用消息窗口 HWND。
- 大上传等待服务器响应时会被全局 45 秒超时截断：上传不设固定总时长；控制请求和下载单块仍有超时。
- 离线意图在队列处理时重连可能被重放：捕获时固定联网资格。
- 切换服务器、旧连接与旧任务迟到：按 server_id、连接代数和设置代数隔离。
- 登记后准备阶段崩溃、下载重试预算重置：持久捕获和重试次数。
- 读剪贴板临时失败提前消耗序号、macOS 自身写入竞态：成功读取后推进序号，并用自身写入标记核对。
- TAR 隐式父路径名称冲突、并发磁盘写、另存为期间缓存回收：补充安全检查及引用保护。
- 浮层旧准备事件抢占和终态回退：后端退役任务集合与终态锁。
- 开发构建签名变化导致钥匙串授权卡住主线程：移至后台，等待/失败时本地历史和窗口仍可用。用户已在系统弹窗完成一次授权；没有绕过系统保护。最终同一构建在独立验收配置中验证了保存和重启恢复。
- 粘贴配对串被捕获为普通历史：排除自身 `easycopy1:` 格式（包括无效/截断串）；显式复制也拒绝。实机检查最终验收配置的 settings/history/cache 均无配对串。

### 修复

- `clipboard/windows.rs` 原来在 `CloseClipboard` 前返回序号。实机写文本后，返回值为 971，而调用返回后实际值为 974，下一次写入被错误拒绝，原生探针稳定失败。现在先关闭、重新打开并核对 owner，再返回实际序号；如果已有其他 owner，则返回旧写入序号，避免屏蔽外部新复制。探针增加文本、图片及文件写入后序号一致性断言，修复后通过。
- 平台依据：[Windows 自动转换剪贴板格式](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats)、[GetClipboardOwner](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardowner)。具体序号变化来自本机回归断言，不把文档描述当作实测。
- 新增 `tauri.windows.conf.json`，Windows 默认安装包目标为 NSIS，保留 macOS 的 app 配置；本轮实际构建为内嵌前端的独立 EXE，未验证 NSIS 安装。
- 新增 `Start-EasyCopy.cmd` 和 `script/build_and_run.ps1`。首次构建、后续直接运行 `.local/windows-client/EasyCopy.exe`；`-Build` 更新构建，`-Dev` 启动 Tauri 开发模式，`-Acceptance` 使用隔离配置。不会主动终止已有客户端。
- 窗口 builder 改为 macOS 条件遮蔽变量，消除 Windows 的 unused_mut 警告；未调整界面或产品行为。
